# V4：统一成员资料与科研内容数据库

- 状态：2026-11-06 用户批准实施；代码与隔离验收完成，等待负责人验收和部署确认。实际结果见 [V4验收报告](../docs/V4-验收报告.md)。
- 位置与分支：`/opt/Lab_web` / `arc-update`。
- 共同契约：[总体规划](V4-V9-后续开发总体规划与验收基线.md)。本阶段完成后单独验收，不自动进入 V5。

## 1. 现状、目标与范围

现有 User 只有基础姓名、账号邮箱等字段，不能承担成员履历和科研成果。静态成员页和论文列表没有可复用的数据库关系。

建立一套能长期承接审核、展示和统计的数据模型，证明一篇论文关联多人、每人汇总准确且不复制论文。保留 accounts 的主键、迁移历史和 API；不重建 Django 项目，不替换静态官网。本阶段交付模型、受控内部读写服务、本人草稿资料 API 和测试；不开放未经审核的公共内容 API，不实现完整投稿后台或批量迁移。

## 2. 模块与表设计

### 2.1 成员体系（apps.members）

| 模型 | 核心字段与约束 | 隐私/生命周期 |
| --- | --- | --- |
| MemberProfile | UUID、可空 OneToOne(User)、membership_status（内部即时资格）、privacy_gate、merged_into（可空自关联）、draft/published_revision、lock_version、created_by/updated_by、时间 | 账号可未绑定；User 绑定数据库唯一；禁止公众按 User ID 读档案 |
| MemberRevision | profile、递增 number、member_kind、public_member_status、display_name、slug、bio、public_contact_email、public_contact_enabled、avatar_asset、状态、编辑者、时间 | 公开字段白名单；slug 的唯一发布占用及别名由服务处理 |
| MemberPrivateData | profile 唯一、phone、内部联络、必要管理备注 | 分表、本人/授权管理者访问，不进入公共 revision 或审计明文 |
| EducationEntry | revision、学校、专业、学位、起止日期、公开选择、排序 | 日期合法；每个版本独立快照 |
| ResearchArea / MemberResearchArea | 规范方向词、revision 关联、排序 | 方向词唯一；展示关联跟随已发布版本 |
| AlumniDestination | revision、毕业年份、学位、去向类别、单位显示名、公开选择 | 毕业去向不创建重复成员；不默认公开工作联系方式 |
| MembershipApplication | applicant、目标 profile 可空、申请类别、状态、证明 asset 可空、审理者和时间 | V4 建表与约束；V5 开放申请/审批流程 |

MemberRevision.member_kind：TEACHER/STUDENT；public_member_status：ACTIVE/ALUMNI/LEFT，属于审核后的公开事实。MemberProfile.membership_status：PENDING/ACTIVE/ALUMNI/LEFT，仅用于内部资格和即时停用，不直接覆盖公共身份事实；公开还须通过 privacy_gate。管理者修改内部资格不应自动改公开成员类别/统计，毕业等公开事实需新版本审核。它们不是 UserRole，不由前端任意赋值。校验开始≤结束，毕业年份范围合理，文本长度有上限；详细个人资料不是注册必填。

### 2.2 通用身份与类型版本（apps.content）

| 模型 | 核心内容 |
| --- | --- |
| ContentItem | UUID、kind、created_by、last_edited_by、created_at/updated_at、published_revision、working_revision、visibility_gate（即时撤下开关）、archived_at、lock_version |
| ContentRevision | UUID、item、number、state、base_published_revision、标题、摘要、编辑人、提交时间；(item, number) 唯一 |
| PaperDetail | revision 唯一、DOI、期刊/会议、发表日期、论文类别、卷期页码、开放链接 |
| ProjectDetail | revision 唯一、项目编号、资助方、级别、开始/结束日期、状态、经费可空且默认内部 |
| AwardDetail | revision 唯一、赛事/奖励名称、级别、奖项、获奖日期；竞赛与其他荣誉用 category 区分 |
| ActivityDetail | revision 唯一、起止时间、地点、受限 Markdown 正文 |
| NewsDetail / BlogDetail | 各自 revision 唯一、正文、事件日期/分类；博客与新闻分表 |
| PublicationDetail | revision 唯一、书名、ISBN、出版社、出版日期、版次；出版刊物独立于论文 |
| LabPageDetail | revision 唯一、固定 page_key(home/about)、简介/正文等受限字段 |
| ContentProjectLink | source_revision、target_project(ContentItem)、关系类型；同 revision/target 唯一 |

kind 是 PAPER/PROJECT/AWARD/ACTIVITY/NEWS/BLOG/PUBLICATION/LAB_PAGE，不设置任意模型名或 ContentType 让客户端指定表。服务层按固定注册表选 serializer/detail，禁止跨类型明细和缺失明细；关键跨表约束在迁移中以 PostgreSQL deferred constraint trigger 检查，事务结束时每个 revision 恰有一个正确明细、指针属于本对象，测试覆盖直接 SQL 绕过 ORM 的失败路径。

DOI 规范化（去 https://doi.org 前缀、去空格、小写）作为 ContentIdentifier 单独唯一占位，关联稳定 ContentItem；已确认 DOI 不因新草稿改变而重复创建。无 DOI 用标题/年份/作者相似度提示冲突，不按标题强制合并。项目编号/ISBN 采用同样规范化与明确唯一范围，ISBN 如不同版次需人工决定，不盲目归并。标识变更必须审核并事务重分配，旧标识保留别名或冲突记录。

### 2.3 贡献者与成员关系

Contributor(UUID、display_name、可空 member_profile OneToOne、external_affiliation)。外部作者没有账号也能成为 Contributor。一个正式成员只有一个规范 Contributor，内容关系引用它；关系表：RevisionContribution(revision、contributor、contribution_role、position、is_corresponding、confirmation_status)。

confirmation_status 仅用作初始状态/派生展示，不允许提交后原地更新；实际确认与争议以 V5 追加确认记录计算。

role 按内容类型白名单：论文 AUTHOR，项目 LEAD/PARTICIPANT，活动 ORGANIZER/PARTICIPANT，出版刊物 AUTHOR/EDITOR，荣誉 WINNER/ADVISOR；新闻/博客可设 AUTHOR。同一贡献者可具有多种职责，但同 revision/contributor/role 唯一；作者 position 唯一且正数，corresponding 可多人。通过 contributor.member_profile 反查成员的已发布成果。

作者顺序与对应关系属于 revision，不引用会随意变化的实时显示名覆盖历史署名；RevisionContribution 保存 approved_display_name/affiliation 快照。外部作者认领绑定需 V5 显式审核，不凭姓名匹配。更新成员名后新展示姓名可用于成员卡片，历史论文署名仍保留。

### 2.4 附件与审计预留

新增 apps.assets 的 AssetFile：UUID、owner、storage_key、原文件名（仅私有）、MIME、size、SHA256、visibility、scan_status、expires_at、created_at。RevisionAsset 与 MemberRevisionAsset 显式外键绑定版本，带 purpose 和排序，不使用裸文件路径。V4 不提供公共上传下载端点。

新增 apps.workflow 的 BusinessAuditLog 与审核状态枚举基础；V4 不复制 AuthAuditLog。内容/成员写入审计只保留字段名与非敏感状态。对绑定、发布指针、重要角色变动不得只靠 signals，使用显式 service + transaction.atomic。

## 3. API 与权限边界

| 路径 | 用途 | V4 开放范围 |
| --- | --- | --- |
| GET/POST/PATCH `/api/members/me/draft/` | 本人档案草稿；PATCH 要求 lock_version | 已登录本人，CUSTOMER 可用；不改 role/绑定/发布状态 |
| GET `/api/members/me/overview/` | 私有档案状态、本人已发布成果计数和引用 | 本人；邮箱电话不进入成果条目 |
| GET `/api/content/participations/` | 当前成员关联已发布成果，分页/类型筛选 | 本人，无权读他人成果草稿 |
| `/api/admin/members/...` | 规范档案建立与绑定 | V4 仅服务和测试；V5 实际开放并配套审核 |

Content 创建服务供测试/后续 V5 调用，不提供无审核 publish 接口。GET 永不创建业务对象，无档案时返回明确空状态；带 CSRF 的 POST 在事务中创建一份 PENDING 草稿，已有时返回该草稿，不重复建档；PATCH 只更新已存在草稿。已绑定档案不能自助更换 user。修改个人草稿成功不改公开指针。

请求示例（省略 Cookie/最新 CSRF 头，实际必须携带）：

```json
{"lock_version": 2, "display_name": "示例成员", "bio": "控制理论方向", "public_contact_enabled": false}
```

返回 draft UUID、lock_version、字段错误和状态；不得包含账号权限字段的可写入口。版本过期返回 409，未登录沿用 403，非本人对象 404。User 修改姓名不自动覆盖审核后的成员名。

## 5. 必须实际验收

沿用总体规划的隔离检查命令；另执行：

```bash
# 由测试工具注入隔离连接，非默认业务库
python manage.py test apps.members apps.content apps.workflow apps.assets --verbosity 2
python manage.py sqlmigrate content <本次迁移编号>
python manage.py showmigrations
```

实施时将占位迁移编号替换为实际编号记录。必须覆盖：

1. 同论文关联三位成员/外部作者，论文仅一个 UUID；按成员反查正确且不重复计数。
2. 一个账号只能绑定一个档案，并发认领不能成功两次；删除/停用账号不删除历史成果。
3. PAPER 不允许 ProjectDetail；published_revision 不能指向他人对象；直接 SQL 触发约束也失败。
4. DOI 规范化重复与并发创建只留一项；无 DOI 相似题名只提示、不误合并。
5. 作者排序/职责约束与角色白名单；毕业档案与教育经历验证。
6. 未登录、CUSTOMER、本人、他人、普通管理者、ROOT 的对象/字段权限；枚举私密 UUID 不泄露。
7. 草稿修改不改变已发布快照；公共序列化不含账号邮箱、电话、私密附件或经费。
8. 从已有 V3 数据迁移后 User、Session、AuthAuditLog 保留；旧认证与 health 全部回归。

预期：check 无错误、无缺失迁移、隔离库迁移全成功、全部新增及旧测试通过。报告记录数量，不能只贴测试计划作为结果。V4 未开发页面则浏览器运行原有 V3 全套，新增 API 用后端真实请求测试。

## 6. 风险、回退与交付门

最大风险是把角色与成员身份绑定、全局关联不随版本、分表跨表约束遗漏。用固定类型服务、数据库约束和负向测试保障。旧静态资料未导入前不据其内容自动创建真实账号。

本版本仅扩展迁移；应用回退到 V3 镜像并停用新 API，保留新表，禁止删除 User 或生产卷。新表有业务写入后不盲目 reverse；先导出/备份并经负责人批准处理。交付 ER 图、字段字典、权限表、实际迁移/测试报告和下阶段接口约束；负责人验收通过才进入 V5。
