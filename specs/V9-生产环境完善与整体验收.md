- 状态：用户已明确授权连续实施，最终统一验收；前置 V4–V8 逐阶段验收，无未解决必需测试失败。
- 工作目录 `/opt/Lab_web`，分支 `arc-update`；遵循[总体规划](V4-V9-后续开发总体规划与验收基线.md)。
- V9 是生产完善门，不是前期放松安全的理由；任何上线、main 合并和服务配置变更仍需明确授权。

## 1. 目标、输入与边界

形成可日常使用、可维护、可恢复的团队平台，不重建数据库/Compose/Nginx，不引入无证据支撑的高可用集群。域名、DNS、证书方式、ECS安全组、备份存放位置/保留与告警收件人需由负责人提供或确认；文档可先用占位，但未获真实配置不得声称生产验收完成。

开始前核验当前镜像、迁移、资产数量、公开 URL、数据库大小、CPU/内存/磁盘、已有系统 Nginx 配置和用户本地改动；只记录脱敏摘要。列出 V1–V8 未验证事项，例如物理手机、Safari和真实 AI 调用，纳入本阶段门禁。

## 2. HTTPS 与会话代理安全

- 使用现有系统 Nginx 单实例配置指定域名证书和续期，先 `nginx -t` 再经授权 reload；不启动 Compose Nginx，不使用默认域名放宽 Host。
- HTTP 跳 HTTPS，API/登录不经明文提交真实密码；先确认证书链、域名、跳转和回环探针，再启用 Secure Cookie、精确 CSRF_TRUSTED_ORIGINS、生产 ALLOWED_HOSTS、DEBUG=False。
- Nginx 明确覆盖而非透传 X-Forwarded-Proto/Host，后端只信任经验证的代理链；配置 SECURE_PROXY_SSL_HEADER 前证明客户端不能伪造协议/来源。后端仍只对回环发布端口。
- 当前限流依赖 REMOTE_ADDR，在 Nginx/Docker 后可能所有人共享同源。仅在可靠代理边界解析真实客户端 IP，过滤用户伪造 X-Forwarded-For；测试多客户端隔离/同客户端一致，不能盲信首个头。
- 初期 HSTS 短周期，确认所有入口 HTTPS后逐步延长；不默认 includeSubDomains/preload，以免影响未准备子域。CSP 先 report-only 观察原页面内联脚本再收紧，不一刀切破坏旧官网。
- Session/CSRF Cookie、HttpOnly/SameSite、点击劫持、nosniff、下载 Content-Disposition、认证/私有响应 no-store 逐项验证。CSRF 轮换/Origin/跨站写拒绝必须真实 HTTPS 浏览器测试。

## 3. 数据库、文件与密钥

PostgreSQL 无宿主公网端口；生产分离运行账号与迁移/备份权限，运行账号不授 superuser/CREATEDB。测试账号只在隔离测试环境具备建测试库权限，不能为让测试方便提升生产账号。审查公网安全组仅保留业务所需与受控 SSH。

代码与 `.env.example` 只包含变量名/占位。真实 `.env` 0600、受控备份，AI key 可轮换；日志不记录 Authorization/Cookie/正文密钥。验证容器 inspect/config 输出的访问范围，不把含环境值的完整输出贴进报告。

文件库默认私有、无目录列表、不可执行；抽查未发布/被撤下附件和缩略图拒绝访问。补齐病毒扫描/文件检测能力并记录依赖与处理失败策略（无法完成检查的文件保持隔离）；资源配额、磁盘水位与清理任务避免媒体占满系统盘。

## 4. 备份与真实恢复演练

拟目标：RPO≤24小时、RTO≤4小时；由负责人批准并在实际数据规模演练后确定，不把目标写成实测成绩。日备 PostgreSQL custom-format、媒体增量与清单，周全量；建议保留7日/4周/3月，至少一份加密异机存储。备份密钥与备份分开保管，访问仅授权运维。

备份窗口暂停业务写入/AI apply/worker，或采用能证明一致性的快照流程，记录同一批次数据库dump、媒体清单、SHA256、准确应用SHA/镜像、迁移版本和UTC时间。备份失败报警，不用空文件覆盖上一份。

拟提供并测试 `deploy/scripts/backup.sh`、restore-verify.sh：前置检查、严格错误处理、原子完成标记、不回显凭据、拒绝目标为生产的默认恢复。执行示意：

```bash
# 待实现脚本；审批后才在真实环境运行
bash deploy/scripts/backup.sh --output <受控备份目录>
bash deploy/scripts/restore-verify.sh --backup <批次清单> --target <独立演练库与媒体目录>
```

演练必须真正 pg_restore 到独立数据库和独立媒体目录，运行迁移一致性、行数/关联/哈希对账，启动隔离应用验证登录（测试账号）、公开版本、私密权限、附件与 AI草稿；验证数据库/文件配对、无生产覆盖。记录恢复耗时、备份生成时间、丢失窗口与实际RPO/RTO。仅 `pg_restore --list` 不能算恢复演练。

回到生产的灾难恢复需单独审批停写与恢复点，保留故障现场及恢复前备份；不能把测试演练脚本默认为覆盖生产。恢复后密钥/Session是否失效及新写入处理列出操作步骤。

## 5. 性能、可靠性、监控与任务

- 对成员主页、论文/项目列表、审核任务、公共搜索、统计做真实 EXPLAIN 与并发测量；处理 N+1、缺索引、无界分页、慢事务及 worker 竞争。合成数据只用于隔离库，不向生产灌压测数据。
- 拟测试负载：30并发读、5并发写，持续10分钟，1万内容/5万关系；普通 API P95≤1s、统计冷查询≤2s、错误率<1%。实际 SLA 需结合 ECS规格调整并经评审；报告分接口的完整分布，不隐藏失败请求。
- 持久任务重启/DB短暂断开/供应商429/磁盘不足故障注入，在隔离环境验证降级、lease恢复、预算不重复消耗与不出现半发布。
- `/api/health/` 保留数据库真实检测；补充 readiness（依赖必需资源）与 worker 心跳，AI非必需故障不使官网全站不可用。健康响应不泄漏版本密钥/数据库连接串。
- 结构化脱敏日志与 request_id，日志轮换保留期、磁盘报警；监控后端/DB/worker 状态、5xx、慢请求、队列积压、AI预算、证书到期与备份失败。告警渠道待负责人指定并明确授权测试通知，不擅自给他人发消息。
- systemd timer/cron 的备份、媒体清理、Session/throttle 清理明确时区、账号、锁与失败告警，定时任务只有经授权才安装；禁止多个节点重复跑破坏性清理。

## 7. 实施与部署顺序

1. 盘点待验证项、资产和生产参数；冻结发布范围，确认域名/备份/告警与性能目标。
2. 在隔离测试运行现有全部 Django/浏览器测试，补安全、恢复、故障和性能用例。
3. 完成脚本、配置模板和手册，演练备份恢复与应用回退；生成具体部署差异。
4. 负责人审阅实际报告并批准准确 SHA、维护窗口和线上变更范围，再执行生产步骤。
5. 备份→验证备份→配置语法检查→迁移预检→兼容迁移→更新应用→HTTPS/代理配置→冒烟→观察，任一步失败停止。
6. 通过后由负责人另行确认 main 合并及正式发布；不把 arc-update已推送视为上线批准。

生产命令写入最终部署手册，以下只是待执行验证清单，不能直接在未准备环境运行：

```bash
docker compose config --quiet
docker compose run --rm backend python manage.py check --deploy
docker compose run --rm backend python manage.py makemigrations --check --dry-run
docker compose run --rm backend python manage.py migrate --check
sudo nginx -t
docker compose ps
curl --fail-with-body https://<正式域名>/api/health/
```

`check --deploy` 的每条警告必须修复或有负责人批准的具体现实理由，不能默认忽略。完整自动化测试在隔离环境执行，生产只受控冒烟，不能创建/删除大量真实账号。域名占位必须替换后执行，实际报告不得保留假命令说已成功。

## 9. 回退和事故处理

HTTPS先验证再扩大重定向/HSTS；证书/代理异常回退经过语法检查的旧配置并保持真实账号不经明文登录。应用回退用记录的旧镜像/兼容schema，不回滚删除生产数据；索引变更有锁/超时策略。数据库损坏按单独批准灾难恢复流程停写处理，明确新写入损失和媒体一致性。

保持问题现场、脱敏日志与审计，先阻止泄露/错误发布再修复。不得通过清空数据库、重置所有账号、删除失败测试或隐藏错误率让验收通过。
