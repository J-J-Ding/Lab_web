## 2. 方案与待确认默认值

采用 Django 原生数据库 Session、DRF SessionAuthentication、Django CSRF 和密码验证器；复用 PostgreSQL 保存审计及限流状态。数据库行锁与事务保证多个 Gunicorn worker 共享计数及权限修改一致性。

不采用每进程 LocMem 限流，因为现有 Gunicorn 有多个 worker，内存计数不能可靠共享；Redis 能实现共享限流，但增加服务，本阶段直接复用 PostgreSQL。Session 是本次明确指定的认证方式，不引入 Token。

以下细节为本 spec 提议，批准本 spec 后落实：

1. 增加 `GET /api/auth/csrf/`，供没有模板页面的 API 客户端首次取得 CSRF Cookie。
2. 在指定的 `GET /api/auth/me/` 同一路径增加 PATCH，实现普通用户修改自己的姓名和 email；没有此入口，用户提出的自助账号信息修改需求无法完整交付。
3. 用户名作为登录标识，创建后不可通过 API 改名；姓名和 email 可修改，email 本阶段不用于登录或找回密码，不声明其已验证或唯一。
4. 非 ROOT 不得通过任何入口更改自己的 role，TEACHER 不能借管理自己的对象绕过个人接口限制。
5. 管理列表只显示调用者可管理的账号；对不可管理目标和不存在 ID 均返回 404，避免泄露 ROOT/ADMIN 信息。
6. 成功修改自身密码保留当前登录，但废止其他旧 Session；管理端密码重置使目标所有旧 Session 在下次访问时失效。禁用账号后，即使重新启用，也不能恢复禁用前的 Session。

## 3. 角色、对象与字段权限

权限判定只使用服务器数据库中的当前身份，不使用请求传入的 actor、role、is_staff 或 is_superuser。

| 调用者 | 可读写管理对象 | 可创建/赋予的业务角色 | 自助操作 |
| --- | --- | --- | --- |
| ROOT（is_superuser=True） | 全部账号，含 ADMIN、ROOT | ADMIN、TEACHER、STUDENT、CUSTOMER | 查询/修改自身资料与密码 |
| ADMIN | is_superuser=False 且 role 属于 CUSTOMER/STUDENT/TEACHER 的账号 | CUSTOMER、STUDENT、TEACHER | 查询/修改自身资料与密码 |
| TEACHER | 与 ADMIN 相同 | CUSTOMER、STUDENT、TEACHER；不能改变自己的 role | 查询/修改自身资料与密码 |
| STUDENT/CUSTOMER | 无管理权限 | 无 | 仅自身资料与密码 |
| 未登录或已禁用 | 无 | 公开注册固定 CUSTOMER | 取得 CSRF、注册、登录 |

- `is_staff` 不授予业务管理权限；role 也不自动设置 is_staff/is_superuser。先判断 ROOT，再判断业务角色。
- 标记为 is_superuser 的目标无论 role 为何均按 ROOT 保护，包括 role=CUSTOMER 的 ROOT。
- 任何 HTTP API，包括 ROOT 调用管理 API，都不能创建 ROOT 或写 is_superuser/is_staff/groups/user_permissions；ROOT 只能通过服务器命令创建。
- 自助 PATCH 仅接受 first_name、last_name、email；管理 PATCH 仅接受 first_name、last_name、email、role、is_active。密码只能通过专用接口修改。
- 创建账号允许 username、password、first_name、last_name、email；管理创建额外允许 role、is_active。公开注册拒绝 role、is_active 等越权字段，不能静默保存它们。
- 对每个输入使用显式字段白名单，未知字段返回 400；不得使用任意字段批量赋值。
- CUSTOMER/STUDENT 对任意管理路由返回 403；对他人 ID 的请求同样拒绝。管理者读写不可管理对象返回 404；对可管理对象提交越权字段/角色返回 400/403，数据库和审计中不得发生成功修改。
- 校验行为人和目标的最新权限、执行修改、写成功审计在同一事务内完成。涉及两人的操作按主键顺序加行锁；重新加载行为人，防止其已降权却继续写入，以及目标刚提升为 ADMIN/ROOT 后被普通管理者接管。

## 4. API 契约

只接收 JSON 请求，返回 JSON；受保护接口匿名或无效 Session 按 DRF SessionAuthentication 语义返回 403，不重定向 HTML 登录页。登录凭据错误使用统一 400 响应，不区分账号不存在、密码错误或账号已禁用。输入错误 400、对象不存在/不可见 404、方法不允许 405、限流 429，并附 Retry-After。

| 方法与路径 | 身份 | 请求/行为 | 成功响应 |
| --- | --- | --- | --- |
| GET /api/auth/csrf/ | 公开 | 设置 csrftoken Cookie，Cache-Control: no-store | 200，`{"detail":"CSRF cookie set"}` |
| POST /api/auth/register/ | 公开，必须 CSRF | username、password，其他仅允许姓名和 email；创建 CUSTOMER，不自动登录 | 201，安全用户对象 |
| POST /api/auth/login/ | 公开，必须 CSRF | username、password；Django authenticate/login | 200，安全用户对象，Set-Cookie 创建/轮换 Session |
| POST /api/auth/logout/ | 已登录，必须 CSRF | 空对象；flush 当前 Session | 204，无响应体 |
| GET /api/auth/me/ | 已登录 | 查询当前数据库身份 | 200，安全用户对象 |
| PATCH /api/auth/me/ | 已登录，必须 CSRF | 仅 first_name、last_name、email | 200，安全用户对象 |
| POST /api/auth/change-password/ | 已登录，必须 CSRF | old_password、new_password | 204；保持当前 Session，其他旧 Session 失效 |
| GET /api/admin/users/ | ROOT/ADMIN/TEACHER | 过滤可管理账号；分页 page/page_size，默认 20、上限 100，按 id 排序 | 200，count/next/previous/results |
| POST /api/admin/users/ | ROOT/ADMIN/TEACHER，必须 CSRF | username、password、允许的资料和 role/is_active；默认 CUSTOMER | 201，安全用户对象 |
| GET /api/admin/users/{id}/ | ROOT/ADMIN/TEACHER | 对象级权限检查 | 200，安全用户对象 |
| PATCH /api/admin/users/{id}/ | ROOT/ADMIN/TEACHER，必须 CSRF | 允许的资料、角色和启停状态 | 200，安全用户对象 |
| POST /api/admin/users/{id}/reset-password/ | ROOT/ADMIN/TEACHER，必须 CSRF | new_password；对象级权限检查 | 204，使目标旧 Session 失效 |
| GET /api/health/ | 公开 | 保留 V1 查询和 200/503 契约，不创建 Session | 200/503，与 V1 一致 |

安全用户对象只包含 id、username、first_name、last_name、email、role、is_active、is_superuser、date_joined。is_superuser 是 ROOT 身份标识，可以在有权限的用户对象中展示，但只读；绝不输出 password、密码哈希、Session 值、内部权限表或限流标识。认证和用户信息响应禁止缓存。

密码调用 Django validate_password，绑定目标用户资料，拒绝常见密码、过短密码、全数字及与用户资料相似密码。密码输入 write_only，长度设置有限上限（建议 128），不自动 strip 密码；旧密码不正确不得修改数据或产生成功日志。用户名重复等数据库约束冲突需转换为稳定 400，不能返回 500。

## 5. Session、CSRF 与生命周期

- 安装 django.contrib.sessions 并新增其标准迁移，不重写既有 accounts/0001_initial。
- SessionMiddleware 在 AuthenticationMiddleware 前，启用数据库 Session backend；DRF 默认启用 SessionAuthentication，保持 IsAuthenticated 默认权限。健康检查仍显式不使用认证。
- 对注册和登录等匿名写接口显式应用 csrf_protect。仅启用 SessionAuthentication 不够，因为它不会为匿名登录请求完成 CSRF 校验；受保护写接口也必须校验 CSRF。
- 客户端先 GET csrf，携带 Cookie 和 X-CSRFToken 进行 POST/PATCH；登录会轮换 CSRF，登录成功后读取新的 csrftoken，不复用登录前 token。
- CSRF 不等于 Session 密钥，可以通过 Cookie 交给客户端；sessionid 只走 HttpOnly Cookie，不放入 JSON 或日志。Cookie SameSite=Lax，Session 有限有效期（建议 8 小时）。
- 当前仅回环 HTTP 验收，Secure Cookie 默认关闭；增加显式环境开关供未来 HTTPS 上线启用。保留 DEBUG=False，不放开通配 ALLOWED_HOSTS/CSRF_TRUSTED_ORIGINS，不信任任意来源的转发请求头，不新增 CORS 通配。
- 登录使用 Django login 轮换 Session 防固定攻击；退出 flush 当前 Session。修改密码使用 set_password 与 update_session_auth_hash；重置密码依赖 Django auth hash 检查让旧 Session 失效。
- 新增 User.session_version（非敏感整数），禁用账号时事务内递增；Session 中记录登录时版本，自定义认证在每次受保护请求中校验。版本不一致即失效，防止禁用后重新启用导致旧 Session 重新可用。已有缺少版本标记的登录 Session 也按失效处理。
- 每次请求从数据库读取 is_active 与角色，已有 Session 不能保留降权前的权限。不以读取 django_session 全表并反序列化每条 Session 作为日常禁用实现。

## 6. 暴力破解防护与审计

### 6.1 共享限流

新增 LoginThrottleBucket，包含 scope、key_digest、attempt_count、window_start、expires_at；scope+key_digest 唯一，过期时间索引。key 使用 SECRET_KEY 派生 HMAC，不保存原始用户名/IP。

建议登录限额：同一 IP+规范化用户名 15 分钟内最多 10 次尝试，同一 IP 15 分钟最多 60 次；所有提交均计数，不因成功登录自动清零。配置项 AUTH_LOGIN_WINDOW_SECONDS=900、AUTH_LOGIN_ACCOUNT_IP_LIMIT=10、AUTH_LOGIN_IP_LIMIT=60。参数必须为正整数。

通过 PostgreSQL 原子创建/行锁更新计数，处理并发首次创建冲突；在密码哈希校验前占用计数，超额返回 429。未知账号、错误密码、禁用账号不能绕过计数；畸形请求至少计入 IP 限额。过期后自然开启新窗口；提供清理过期桶的服务器命令，不能靠重启 worker 重置防护。

本阶段信任 REMOTE_ADDR，不直接信任用户提交的 X-Forwarded-For；当前回环访问的 IP 可能是 Docker 网关，测试需考虑共享限额。将来接入 Nginx 时必须单独确认可信代理配置，再调整真实客户端 IP 获取；不能因伪造请求头绕过限制。

### 6.2 审计

新增 AuthAuditLog：actor（可空）、target（可空）、actor_id/target_id 的稳定快照、action、outcome、changed_fields、非敏感角色/启停前后值、created_at、来源 IP 的 HMAC 摘要。ROOT 初始化时 actor 为空且 action 明确为服务器命令。账号主键快照避免将来删除账号后丢失历史归属。

记录成功创建账号、登录成功/失败/限流、退出、修改个人密码、管理重置密码、角色变更、账号启停及管理资料修改；已通过 CSRF 的敏感管理拒绝也记录精简 denied 事件。不得保存原始请求、完整序列化 User、密码/旧密码/新密码、密码哈希、Cookie、Session/CSRF token；姓名/email 修改只记录字段名，不复制值。

敏感成功操作与审计写入共用事务：审计失败，操作回滚，不得“密码已重置但日志没有”。拒绝日志在不修改账号的路径单独持久化，不因回滚成功事务而消失。日志不开放修改/删除 API，运维查询通过服务器命令或 ORM；本阶段不开发审计前端。

## 7. ROOT 初始化

新增 `python manage.py init_root --username <用户名>`：仅在服务器交互输入密码（getpass，两次确认），不支持命令行 password 参数、不读取默认密码、不向控制台打印密码。

- 验证 username、密码及确认一致，创建 is_superuser=True、is_staff=True、is_active=True 的 User，role 默认 CUSTOMER，使用标准密码哈希并写审计。
- 同名账号已经存在时拒绝操作，不能把公开注册的同名普通账号自动提升为 ROOT，也不能重置现有 ROOT 密码；失败不产生半成品账号。
- 不通过网页/API 创建 ROOT。保留 Django 原生 createsuperuser 作为服务器能力，但项目部署说明统一使用 init_root；API 不暴露任一命令。
- 实施验收只在隔离测试库创建测试 ROOT；真实 ECS 的 ROOT 由用户运行交互命令设置，不由自动化过程创建未知密码的真实账号。
- 不将真实 ROOT 用户名/密码写入源码、.env.example、测试报告或 shell 历史。

| 原健康接口 | 匿名真实 SELECT 1、200/503、无额外 Session/认证查询；原测试继续通过 |

测试使用 Django 创建的独立 test_lab_web，不清空、替换、覆盖现有主库。并发测试使用 PostgreSQL 和 TransactionTestCase，不能用 SQLite/进程内缓存代替。测试必须对每种管理角色分别执行，不以一个 ADMIN 测试替代 TEACHER。
