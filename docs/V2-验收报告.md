## 真实双 worker HTTP 验证

测试在独立 lab_web_v2_http_20261105 数据库和不发布宿主机端口的临时服务中执行。驱动在 `backend/apps/accounts/tests/http_smoke.py`，先验证独立数据库前缀、实际 current_database 与空用户表，然后只在该库通过管理命令创建随机密码的测试 ROOT。密码、Cookie 均不输出。

最终镜像上实际执行：

```bash
sudo -n docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" lab_web_v2_http_20261105'
sudo -n docker compose run --rm --no-deps -e POSTGRES_DB=lab_web_v2_http_20261105 backend python manage.py migrate --noinput
sudo -n docker compose run -d --rm --no-deps --name lab-web-v2-http -e POSTGRES_DB=lab_web_v2_http_20261105 backend gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 2 --access-logfile - --access-logformat '%(p)s %(m)s %(U)s %(s)s'
sudo -n docker exec lab-web-v2-http python -m apps.accounts.tests.http_smoke
sudo -n docker logs lab-web-v2-http

sudo -n docker compose exec -T db sh -c 'dropdb -U "$POSTGRES_USER" lab_web_v2_http_20261105'
```

上述指定数据库专供本次验证，已清理；不得将 createdb/dropdb 或驱动指向真实业务库。日志验证实际登录请求分别由 PID 13、14 处理，两个 Gunicorn worker 均参与，并在共享计数达限后返回 429。

驱动输出：`http_checks_passed=69, failed=0, skipped=0`。含真实 CSRF Cookie、登录/改密/重置/启停、退出 Cookie 重放、角色权限、ROOT 保护、429 Retry-After、审计敏感值排除及 health。预期拒绝的 400/403/404/429 也经过逐条状态断言，不是将所有非 2xx 忽略为通过。

## 失败修复与独立审阅

1. API RED 阶段 26 项测试均因路由未实现而失败，另有 Session 尚未安装引起的错误；实现后基础 38 项通过。
2. 安全测试发现不可见 ROOT 的 404 拒绝缺少审计，已补充 Http404/NotFound 拒绝记录及稳定目标快照；ROOT/清理命令从缺失到实现，正反测试均通过。
3. 并发测试最初读取了 PostgreSQL 事务内缓存的统计快照，误判无锁等待。按官方统计语义在观察前 pg_stat_clear_snapshot，保持原有锁等待与拒绝断言；真实权限重检测试通过。
4. HTTP 验证工具的 CookieJar 不能 deepcopy（含 RLock），改为复制各 Cookie；修正临时容器重跑清理流程后，对空隔离库重新跑完 69 项，工具错误没有忽略。
5. 独立审阅发现 NFKC 后可能形成非法用户名。主代理按实际账号可用性将其作为需要修复的输入校验问题处理；API 回归先观察到错误 201，再在规范化后重新校验用户名，转为 400。合法全角用户名仍可按返回的规范用户名登录。最终完整 58 项及 69 项 HTTP 均重新通过。

独立审阅检查授权、字段、CSRF、Session、锁、审计、限流和命令，未发现可提权路径；上述输入问题已修复，无遗留审阅问题。审阅者未独立执行部署/测试、读取真实数据或审计宿主机，本报告中的运行证据由主代理实际执行获取；不把审阅意见代替测试结果。
