# 备份与恢复

`bash deploy/scripts/backup.sh --output /opt/lab-web-backups/<新批次>`：暂停运行中的backend/worker，PG custom-format和私有媒体一致备份，逐表行数与内容摘要、文件SHA256、镜像/提交/UTC时间、COMPLETE完成标记；严格失败则恢复原服务并拒绝输出不完整批次。输出目录不得是frontend，权限0700/0600，不覆盖已有备份。

`bash deploy/scripts/restore-verify.sh --backup <完整批次目录> --target lab-web-restore-<名称>`：内部附加随机唯一项目名，拒绝已有资源；使用独立PostgreSQL容器和卷，无宿主端口，pg_restore真实恢复，安全解包独立媒体，核对各表摘要及文件包SHA，完成后只清理本次演练资源，绝不恢复到正式项目。脚本不用于生产灾难覆盖；后者需要停写、故障现场保留和明确恢复点批准。

本次真实演练成功还原49张表及6个私有文件，逐表摘要一致，耗时39.02秒（含容器就绪与清理环境负载）。这是当前小数据规模恢复测量，不是未来大数据RTO承诺。目标RPO≤24h/RTO≤4h，定时任务尚未安装，不能宣称已实现24h自动RPO。

systemd service/timer仅模板，未安装；时区Asia/Shanghai，flock防并行。同机保留7日/4周/3月、加密异机副本目的地和密钥由负责人确定，不能把同机备份当灾备。证据在服务器受控备份目录，不提交真实dump/媒体到Git。恢复后若密钥变更，明确Session失效策略；不要重置所有账号作为修复方式。

补充实际演练：恢复库启动当前应用、迁移检查、随机测试账号登录/匿名拒绝/缺失CSRF拒绝均通过；还逐个核对可用资产字节SHA256与恢复数据库元数据，最近一次30.84秒。演练绑定媒体由恢复执行者拥有，探针以该UID运行；真实灾难恢复需要恢复目标应用用户的卷权限，不应把一次受控探针等同正式生产权限验收。
